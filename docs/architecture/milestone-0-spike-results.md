# Milestone 0 compatibility spike results

Status: **exit criteria met** on 2026-11-21. Evidence is regenerated by
`spikes/milestone-0/run-spike.zsh`; generated artifacts are not committed.

## What was exercised

The spike runs a real pinned Pi agent loop against the existing Marga tree,
which is imported read-only from `~/codebox/marga`. Two loopback services stand
in for infrastructure that is not part of this repository:

- an OTLP/HTTP trace receiver (`127.0.0.1:4318`) that decodes protobuf and JSON
  exports and writes them as JSON lines;
- a deterministic OpenAI-compatible provider (`127.0.0.1:8091`) that emits an
  `add(a=2, b=2)` tool call and then a final answer, and records the incoming
  W3C `traceparent`.

Marga runs at `127.0.0.1:8011` with OpenLIT instrumentation installed around its
ASGI app. Its route is pinned to the deterministic backend because the local
llama.cpp model at `127.0.0.1:8080/v1` does not reliably emit tool calls.

## Reproduction

From the repository root:

```sh
cd spikes/milestone-0
uv sync --frozen
cd pi-runtime && npm ci && cd ..
zsh run-spike.zsh
```

The script starts all three loopback services, waits for their health probes,
runs the Pi task, and then runs `verify_spike.py`, which fails on any missing
criterion. Unit tests are available with `uv run pytest -q` and
`npm test` in `pi-runtime`. Static checks are `uv run ruff check .` and
`npm run typecheck`.

## Findings that affect later milestones

1. **OTLP encodings differ.** Python OpenLIT exports protobuf; TypeScript
   OpenLIT exports OTLP JSON using chunked transfer encoding. OTLP JSON ids are
   lowercase hex, which must not be passed through a generic protobuf JSON
   parser (it treats them as base64). The spike receiver handles both and has a
   regression test for the hex-id case.
2. **Short-lived CLI processes must drain telemetry.** OpenLIT uses a simple
   span processor when `disableBatch` is set; the HTTP export is still
   asynchronous. `run.ts` flushes and shuts down the tracer provider before
   exit.
3. **Pi accepts an `openai-completions` model with a custom `baseUrl` and
   `headers`.** This is the clean boundary for Marga; no Pi source changes are
   needed. The `Agent` event stream maps directly onto tenant-scoped task and
   tool events with sequence numbers.
4. **Marga does not propagate trace headers itself.** The correlation observed
   here comes from OpenLIT's HTTP instrumentation. A production launcher must
   install that instrumentation explicitly; relying on Marga's transport to
   forward arbitrary headers would silently break traces.
5. **llama.cpp tool calling is unreliable with the local Hermes model.** It
   answered arithmetic in prose even with a forced tool choice. The mock
   provider proves the Pi loop and gateway path; a hosted or tool-tuned model
   must be verified before Milestone 1 claims tool support with llama.cpp.
6. **LiteLLM is out of scope for kartā.** It is a Marga concern; kartā
   integrates only with Marga's OpenAI-compatible surface (ADR-003).
7. **Bangtag and original margAI compatibility remain deferred** by the
   maintainer. No JSONL emitter was added to the platform or Pi runtime.

## Gap to the original local setup

The live Marga service at `127.0.0.1:8010` uses `qwen2.5-coder:7b` and
`llama3.2:3b` aliases that do not match the currently loaded llama.cpp model
(`Hermes-3-Llama-3.1-8B.Q4_K_M`). The spike launcher therefore builds its own
backend table instead of loading the dirty `marga.toml`. That file and the
Marga working tree were not modified.
